## 一、系统角色与通信职责

```
┌─────────────┐   BLE/WiFi    ┌──────────────┐        UDP        ┌────────────────────┐
│   AI 眼镜    │ ───PCM 流───→ │  Android App │ ───────────────→  │  Jetson AGX Orin    │
│  CY01_0799  │               │  UDP 客户端   │ ←───────────────  │  UDP 服务端（本文档）│
└─────────────┘               └──────────────┘   文字回复/指令     └────────────────────┘
```

| 角色 | 职责 |
|---|---|
| **Android App** | UDP **客户端**。主动发起握手探测；上传语音/图片；接收后端回复与指令 |
| **Jetson** | UDP **服务端**。监听固定端口；应答握手；接收并处理数据；下发回复与指令 |

**为什么这样分**：Android 侧 IP 会变（眼镜使用 WiFi Direct 时手机网络会变动），而 Jetson 在局域网内地址固定，因此由固定端做服务端。

**已确认的环境事实**：

| 项 | 值 |
|---|---|
| Jetson 局域网 IP | `192.168.0.194` |
| 手机局域网 IP | `192.168.0.167` |
| 网段 | `192.168.0.0/24`（同一网段，无路由障碍） |
| 已验证 | 手机 → Jetson `22` 端口 TCP 可达，网络层通畅 |

## 二、连接方式

### 2.1 传输层参数

| 项 | 值 | 说明 |
|---|---|---|
| 协议 | **UDP（IPv4）** | |
| Jetson 监听地址 | `0.0.0.0` | 监听所有网卡，不要绑定到单一网卡 |
| Jetson 监听端口 | **`1050`** | App 侧默认值，用户可在 App 界面修改 |
| 手机端口 | **系统随机分配** | 手机绑定端口 0，不能假设固定端口 |

> ⚠️ **关键**：App 侧的 socket 绑定到端口 `0`，由系统随机分配源端口。**Jetson 必须从收到的数据包中读取对端地址和端口，并用它回包**，绝不能写死端口或假设手机也用 1050 接收。

### 2.1.1 关于端口 1050 的说明

**① 非特权端口，无需 root**

1050 > 1024，属于非特权端口，**服务端可以直接以普通用户身份运行，不需要 sudo**。

```
./jetson_glasses_backend
```

**② 该端口的背景（不影响使用，仅作记录）**

1050 是 IANA 正式注册端口，服务名 `cma`（CORBA Management Agent），TCP/UDP 均占用。Jetson 上通常不会运行 CORBA 相关服务，因此**不会冲突**。另外该端口历史上曾被 MiniCommand 木马使用，少数安全扫描器会将其标记为可疑端口——在私有内网环境下无实际影响。

**③ 防火墙放行 UDP**

如果 Jetson 启用了 `ufw`，需注意 `allow` 规则默认按 TCP 理解，**必须显式指定 `/udp`**：

```bash
sudo ufw allow 1050/udp
```

> **备注**：端口可随时更改。App 侧无需改代码——连接页的端口输入框可直接修改，历史记录会保存修改后的值。

### 2.2 为什么需要应用层握手

UDP 是无连接协议，`connect()` 在本机只是记录目标地址，**不发送任何数据包**，因此无法通过"建立连接"判断对端是否可达。所以 App 与 Jetson 之间定义了一个**应用层握手**来确认地址可用：

```
手机                                 Jetson
 │                                     │
 │  PROBE (type=1, ts=T1)              │
 │ ──────────────────────────────────→ │  ① 校验魔数/版本/长度
 │                                     │  ② 记录来源地址与端口
 │                                     │  ③ 构造 ACK（ts 原样回填 T1）
 │  PROBE_ACK (type=2, ts=T1)          │
 │ ←────────────────────────────────── │  ④ 发送回来源地址:端口
 │                                     │
 │  ⑤ 校验魔数 + type==2 → 判定地址可用   │
 │  ⑥ 进入已连接状态，开始正常收发         │
```

**握手失败的表现**：App 显示"连接失败 — 无响应（已重试 3 次…）"。App 侧有一个「跳过握手校验」调试复选框可绕过，但**正常使用必须实现应答**。

## 三、握手协议（冻结）

### 3.1 报文格式

**16 字节定长，大端序（网络字节序）**

| 偏移 | 长度 | 字段 | 取值 |
|---|---|---|---|
| 0 | 4 | 魔数 | `0x47 0x4C 0x53 0x59`（ASCII `"GLSY"`） |
| 4 | 1 | 协议版本 | `0x01` |
| 5 | 1 | 消息类型 | `0x01` = PROBE<br>`0x02` = PROBE_ACK |
| 6 | 2 | 保留字段 | `0x00 0x00` |
| 8 | 8 | 发送端时间戳 | epoch milliseconds，**大端 uint64** |

### 3.2 时序与超时参数

App 侧固定的探测参数（Jetson 必须在此约束下工作）：

| 参数 | 值 | 含义 |
|---|---|---|
| 单次超时 | **800 ms** | 发出 PROBE 后等待 ACK 的时间 |
| 重试次数 | **3 次** | 含首次，总耗时上限约 2.4 秒 |

> ⚠️ **Jetson 必须在收到 PROBE 后立即回包**。任何延迟都会让第一次甚至第二次探测超时。不要在收到 PROBE 时做磁盘 I/O、模型加载等耗时操作。

### 3.3 Jetson 侧应答要求

1. **原样回填时间戳**（偏移 8~15 使用请求中的值）。App 当前只校验魔数和类型，不校验时间戳，但回填可支持将来做 RTT 测量。**请照做。**
2. **只改类型字节**，其余字节保持与请求一致。
3. **回复到数据包的来源地址和来源端口**，不是固定地址。
4. **只回 16 字节**，不要附加任何额外内容——多余字节可能导致 App 侧解析异常。
5. 收到非法包（魔数不符、版本不符、长度不足 16）**直接丢弃**，不要回包。

### 3.4 报文示例

**PROBE（手机发出，ts = 1791894000000 = `0x000001A12C4E8900`）**

```
47 4C 53 59 01 01 00 00 00 00 01 A1 2C 4E 89 00
└─"GLSY"─┘ │  │  └─保留─┘ └────时间戳(大端)────┘
         版本 类型=PROBE
```

**PROBE_ACK（Jetson 应答，仅类型字节变化）**

```
47 4C 53 59 01 02 00 00 00 00 01 A1 2C 4E 89 00
                ↑ type=2
```

## 四、应用层消息协议

握手完成后进入正常通信阶段。所有后续报文复用 §3.1 的 16 字节头（其中偏移 6~15 的字段含义按消息类型重新定义）。

> **说明**：第四章的消息类型定义**供 Jetson 侧实现参考**。App 侧的发送功能尚未实现（见 §7.2），因此这部分的字节布局**尚未冻结**——如果你有更好的设计，现在提出成本最低。

### 4.1 消息类型表

| type | 名称 | 方向 | 载荷 | 本期要求 |
|---|---|---|---|---|
| `0x01` | PROBE | 手机 → Jetson | 无 | **必须实现** |
| `0x02` | PROBE_ACK | Jetson → 手机 | 无 | **必须实现** |
| `0x10` | VOICE_PCM | 手机 → Jetson | 裸 PCM 字节（无文件头） | 收到即落盘 |
| `0x11` | VOICE_META | 手机 → Jetson | JSON：采样率/声道/位深/时长 | 记录日志 |
| `0x20` | PHOTO_JPEG | 手机 → Jetson | JPEG 字节 | 收到即落盘 |
| `0x30` | REPLY_TEXT | Jetson → 手机 | UTF-8 文本 | 预留，本期可不发 |
| `0x31` | CMD_TAKE_PHOTO | Jetson → 手机 | JSON：`{"turn":N,"question":"..."}` | 预留 |
| `0x7F` | HEARTBEAT | 双向 | 无 | 收到即回同类型空包 |

**本期建议先实现**：`0x01` / `0x02`（握手）、`0x10` / `0x11`（语音落盘）、`0x7F`（心跳）。其余类型收到时打日志即可。

### 4.2 ⚠️ 单包大小上限 —— 必须分包

UDP 单个数据报的理论上限是 **65507 字节**（IPv4），超过会发送失败或分片。而实测的语音数据量是：

| 场景 | 数据量 | 换算 |
|---|---|---|
| 3 秒语音 | ≈ 96 KB | 16 kHz × 16 bit × 单声道 = 32 字节/毫秒 |
| 10 秒语音 | ≈ 320 KB | 同上 |

**一条完整语音不可能装进一个 UDP 包，必须分包传输。**

**本期处理方式**：Jetson 侧先按"每个包独立落盘、按递增序号命名"处理，即把收到的每个 `0x10` 包当作一个片段写入文件，**不做重组**。

**下一版会增加分片字段**（序号 / 总数），届时再实现重组逻辑。App 侧 `AiDialogueManager` 已经能产出完整的 `voice_<ts>.pcm` 文件，但目前尚未接入 UDP 发送，见 §7.2。

## 五、收到的数据如何落盘

建议按会话分目录，便于区分不同设备/不同连接：

```
received/
├── 2026-10-13_192.168.0.167_54321/     # 命名：日期_对端IP_对端端口
│   ├── voice_001.pcm                    # 每个 UDP 包一个文件
│   ├── voice_002.pcm
│   ├── meta.json                        # 记录采样率等元信息
│   └── photo_001.jpg
└── ...
```

**会话键建议用「对端地址:对端端口」**。原因：手机每次重连时源端口可能变化，用端口做键可以自然区分不同连接。

**PCM 格式**（与 App 侧一致）：

| 项 | 值 |
|---|---|
| 采样率 | 16000 Hz |
| 声道 | 单声道 |
| 位深 | 16 bit |
| 字节序 | 小端（Android 原生） |
| 无文件头 | 是（裸 PCM，需要时可自行添加 WAV 头播放） |

### 7.1 启动前确认

```bash
# 确认 IP
ip addr show | grep "inet "

# 放行 UDP 端口（注意：ufw 规则默认按 TCP 理解，必须显式指定 /udp）

```

### 7.2 排查对照表

| 现象 | 排查方向 |
|---|---|
| App 显示"无响应" | Jetson 是否在监听（`ss -lunp \| grep ':1050'`）；防火墙是否放行 **UDP** 1050 |
| 防火墙已 allow 但仍收不到包 | 很可能只放行了 TCP——需执行 `sudo ufw allow 1050/udp` 显式指定 UDP |
| App 连上但此后收不到数据 | 回包地址或端口用错——必须从数据包取来源地址和端口，不能写死 |
| 收到的包不完整 | 单包超过 65507 字节会失败，见 §4.2 |
| 换网络后连不上 | App 会先尝试历史 IP、失败后让用户重输——符合预期行为 |

Jetson 端可在**没有手机**的情况下验证握手逻辑。写一个模拟 App 行为的探测程序：

```
参数：
  魔数      = 47 4C 53 59
  版本      = 01
  类型      = 01 (PROBE)
  时间戳    = 当前 epoch millis，大端 8 字节

流程：
  重复 3 次：
```

## 十一、音频回传：Jetson → 手机（2026-10-14 设计；Jetson 侧已实现，App 侧待实现）

### 11.1 概述

LLM/TTS 每产出一段音频（一句话），Jetson **立即**分片回传，不等整段回复生成完毕。
App 收到完整一段即入播放队列，按到达顺序连续播放（即对话的自然顺序）。

```
Jetson: LLM 流式回复 → 切句 → TTS 逐句合成 → 每句完成即刻 UDP 回传（0x32 分片）
App:    按段重组成 16k PCM → 入队 → 顺序播放；被打断则立即停止并清队列
```

### 11.2 消息类型（新增）

| type | 名称 | 方向 | 载荷 |
|---|---|---|---|
| `0x32` | REPLY_AUDIO | Jetson → 手机 | 音频分片（格式与上行 `0x10` 完全一致） |
| `0x33` | REPLY_AUDIO_STOP | Jetson → 手机 | 无（16 字节空包）：立即停止播放并清空回传队列 |
| `0x40` | ABORT_REQ | 手机 → Jetson | 无（16 字节空包）：请求打断当前回传 |

### 11.3 0x32 分片格式（与上行 0x10 一致）

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0..3 | 4 | 魔数 "GLSY" |
| 4 | 1 | 版本 0x01 |
| 5 | 1 | 类型 0x32 |
| 6..7 | 2 | 载荷长度 N（大端 u16） |
| 8..9 | 2 | seq（大端 u16，从 0 开始） |
| 10..11 | 2 | total（大端 u16，本段总片数） |
| 12..15 | 4 | 保留 = 0 |
| 16.. | N | 载荷：16kHz / 16bit / 单声道 / 小端裸 PCM |

- **一段音频 = 一个独立分片会话**（seq 从 0 到 total-1）；一次回复通常有多段（每句一段）。
- 载荷每片 ≤16384 字节；数据报总长 = 16 + N。
- Jetson 发往 App 的**来源地址:端口**（App 发送时所在 socket 的本地端口），App 用同一 socket 即可收到。

### 11.4 App 侧行为（按此实现）

1. **重组**：收到 0x32 按 `seq` 缓存当前段；`seq==0` 视为新一段开始（上一段未收齐则丢弃）。
   收齐 `[0, total)` 全部片 → 该段 PCM 追加到**播放队列**末尾。
   某段超过约 2 秒未收齐 → 视为丢包，丢弃该段继续（不要卡死）。
2. **播放**：按队列顺序逐段播放；16k 单声道 PCM16LE 可直接送 Android `AudioTrack`
   （建议以 16k 采样率创建；设备不支持时重采样到 44.1/48k）。
3. **打断（App 主动）**：用户按键 / 检测到用户再次说话 → 立即停止本地播放、清空播放队列
   与未完成缓冲，并发送 **0x40**（16 字节空包）。
4. **打断（Jetson 主动）**：收到 **0x33** → 立即停止播放、清空队列与未完成缓冲。
   Jetson 在以下情况主动发 0x33：收到新一段用户语音首片（用户又开始说话）、
   Jetson 端键盘新输入、收到 App 的 0x40（可视为对打断的 ACK）。
5. 0x32 / 0x33 不需要回 ACK。

### 11.5 Jetson 侧行为（已实现）

- TTS 每段音频合成完成 → 转 16k PCM16LE（`run_tts.py` 同时产出 `.pcm16k`）→ 立即以 0x32 分片发出；
- 回传目标 = 最近 10 分钟内发来握手/语音/照片/元信息的「地址:端口」；无有效对端时回退本地播放；
- 本轮回复全部音频**发送完毕** → 删除本轮全部 wav/pcm16k 文件，等待下一轮对话；
- 被打断（用户新语音 / 收到 0x40 / 键盘输入 / 清空对话）→ 若回传进行中则发 0x33，
  并删除本轮全部音频文件、停止后续句子的合成与发送（本轮剩余回复不再播报）。
